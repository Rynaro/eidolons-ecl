## S2 — Decisions

### DECISION-S0 — v2.0 (major) not v1.3 (minor)

**Outcome:** **v2.0.0** (MAJOR).

[WHY] The ISE subset chosen in DECISION-S1 changes receiver semantics: at `ise.assertion_grade=validated` AND `constraints.trust_level=high`, the v2.0 conformance gate `S-3` raises a **WARN today / MUST-fail at v2.1+** if a receiver auto-routes to a downstream MUTATING performative (`COMMIT`, `REJECT`) without re-verifying. v1.x receivers cannot anticipate this; therefore v2.0 receivers are not drop-in compatible with v1.x emitter expectations (a v1.x emitter that always expected unconditional auto-route now sees a warn). That is a receiver-semantics change, the canonical SemVer trigger for MAJOR. The schema `$id` URI path segment (`/v1.0.0/` → `/v2.0.0/`) also breaks any external vendor pinning by URI (FINDING-006), which alone is debatable as MAJOR but reinforces the call.

[ALTERNATIVES] (a) v1.3 minor with ISE as pure-additive optional fields and no receiver-semantics change. Rejected because it leaves I-5 SHOULD (DECISION-S9 / GAP-H) and ISE both as WARN-only, undermining the trust-hierarchy story. (b) v2.0 with **strict** MUST-fail S-3 today. Rejected as too aggressive given the 12-month §7.3 window — see DECISION-S9.

[CONSEQUENCES] Schema `$id`s bump in 12 files; URI-pinned external vendors must update; `spec/ecl-2.0.md` ships as a new file alongside retained `ecl-{1.0,1.1,1.2}.md`; `ECL_VERSION` jumps 1.2 → 2.0 in one step.

### DECISION-S1 — GAP-E: ISE field set (the heart of v2.0)

**Outcome:** Three OPT-IN-on-emit / OPT-IN-on-enforce fields, anchored as `envelope.ise.*`:

1. `ise.assertion_grade` — emitter's claim about how the artefact was produced.
2. `ise.provenance` — how-was-it-derived: tool surface + methodology version.
3. `ise.receiver_authorization` — what the receiver MAY do with this envelope.

Field details + JSON Schema fragments in §S3. **Existing `constraints.trust_level` is RETAINED, unchanged in semantics**, and `ise.*` *composes with* it (not replaces). The minimal viable subset closes DC-1 (`$id` bump trigger), addresses T3 (DECISION-S1 strengthens the "what authority does this claim?" answer beyond `from.eidolon` alone), and gives receivers the new normative hook S-3 (DECISION-S0).

[WHY] We need ≥3 fields covering the load-bearing axes of the user's frame: `assertion_grade` covers **what-I-claim**; `provenance` covers **how-was-it-derived**; `receiver_authorization` covers **what-receiver-can-do-with-it**. We drop **who-am-I** (already covered by `from.eidolon@version`+roster cross-check — T3 mitigation) and **who-vouches** (chain-of-trust deferred; introduces nested-envelope-ref complexity orthogonal to S2.3 and would expand schema surface beyond envelope-only).

[ALTERNATIVES]
- (a) Five fields covering all axes. Rejected: bloats v2.0; adds nested-envelope-ref signature chain (who-vouches) which is naturally a v2.1 feature.
- (b) Single `ise.score` numeric (0..1). Rejected: collapses the axes and is unverifiable. The whole point of a hierarchy is dimensional separation.
- (c) Three fields with `provenance` replaced by `evidence_anchor_required: bool`. Rejected: `evidence_anchor_required` already exists as an unused contract-side field (DC-2; FINDING-025), better landed when DC-2 is exercised.

[CONSEQUENCES] `schemas/envelope.v2.json` adds `$defs.ise` (S3); three new conformance gates `S-1`, `S-2`, `S-3` (S4); ISE is **OPT-IN to emit** (envelopes without `ise` remain conformant under v2.0) but **OPT-IN-with-warn-when-missing-and-high-trust** at the receiver (`S-3`). Threat-model T3 directly strengthened; T2 indirectly (via `receiver_authorization` constraining auto-route blast radius).

### DECISION-S2 — GAP-A: per-edge `default_ise` in contracts

**Outcome:** **NO** at v2.0. Defer to v2.1 (or first concrete consumer).

[WHY] Phase 2.C is envelope-only by scoping doc line 210. No contract today carries any ISE-related field (FINDING-008). Adding `default_ise` to contracts requires `handoff-contract.v1.json` `$id` bump to `.v2.json`, which expands the schema-bump radius from 1 file to 2 and pulls in 19 contract files' validation tests, with no concrete consumer pulling on the field. Status: **drift-register candidate** (sibling of DC-2 — unused contract-side fields).

[ALTERNATIVES] Add `default_ise` now and let envelopes inherit. Rejected: no v2.0 emit path consumes it; would be a second unused-contract-field (DC-2 redux).

[CONSEQUENCES] Contracts schema stays at `handoff-contract.v1.json` with **only** the `$id` segment bumped to `/v2.0.0/` (the schema *registry version* bumps; the schema *content* does not). New drift-register entry `D-02` filed: "ISE inheritance from contract defaults — promotion trigger: first per-Eidolon adoption that wants edge-level defaults."

### DECISION-S4 — GAP-C: migrate-backfill + a2a-translate emit version

**Outcome:** **v1.0** (legacy, conservative). Unchanged.

[WHY] `migrate/backfill.py:63` and `a2a_bridge/translator.py:196,205` are **back-fill tools for legacy artefacts** (FINDING-018). [ALTERNATIVES] Flip to v2.0 with `assertion_grade: unverified`. Rejected: deliberately emitting an unverified ISE block is worse than emitting a v1.0 envelope that signals "this is legacy" by omission of `ise`. The §7.3 compat window guarantees v2.0 receivers accept v1.0 envelopes.

[CONSEQUENCES] `reference-sdk/py/tests/test_migrate.py:88,200-210,217,586` v1.0 assertions stay. No regression. `docs/migration-v1-to-v2.md` (NEW) explicitly clarifies the distinction between **back-fill** (still v1.0) and **forward-migration** (operator manually emits v2 envelopes for ongoing artefacts).

### DECISION-S8 — GAP-H: I-5 SHOULD → MUST at v2.0

A v2.0 emitter MAY choose to MUST-fail in *strict* mode, but the default verifier path stays SHOULD to preserve §7.3. Promotion target: v2.1, once HMAC adoption telemetry from the per-Eidolon vendoring cycle (FINDING-026) shows ≥3 of 6 Eidolons routinely emitting `hmac-sha256` at high.

[ALTERNATIVES] Promote now. Rejected: §7.3 violation. Demote to MAY. Rejected: weakens T1 mitigation.

[CONSEQUENCES] `conformance/lib/integrity.sh:117-124` stays warn-shaped; spec text in `ecl-2.0.md` §6.1 calls out the v2.1 promotion path as a [PROMOTION-CANDIDATE]; CHANGELOG `[2.0.0]` "Deferred" subsection records the call.

## S3 — Field reference (the new `envelope.ise.*` block)

The ISE block is OPTIONAL at the envelope root and is **distinct from** `envelope.constraints.trust_level` (which is retained, unchanged). When present, ISE composes with — never replaces — the existing trust model.

### S3.1 — Top-level shape

```json
{
  "ise": {
    "assertion_grade": "validated",
    "provenance": {
      "methodology_version": "spectra-4.3.1",
      "tool_surface": ["read", "grep", "ajv"],
      "lateral_consults": []
    },
    "receiver_authorization": {
      "auto_route": true,
      "auto_merge": false,
      "auto_deploy": false
    }
  }
}
```

### S3.2 — JSON Schema fragment (target: `schemas/envelope.v2.json` `$defs.ise`)


### S3.3 — MUST/SHOULD/MAY (emitter + receiver)

| Rule | Side | Level | Surface |
|---|---|---|---|
| `ise` is OPTIONAL on emit at v2.0. Envelopes without it remain conformant. | Emit | MAY | §6.5.1 |
| When emitted, `ise.assertion_grade` is REQUIRED inside the block. | Emit | MUST | §6.5.2 |
| When `constraints.trust_level=high` AND envelope crosses a mutating-performative edge (`COMMIT`,`REJECT`), emitter SHOULD set `ise.assertion_grade ∈ {validated, human-reviewed}`. | Emit | SHOULD | §6.5.3 |
| Receivers SHALL accept envelopes without `ise` (back-compat). | Receive | MUST | §6.5.4 / §7.3 |
| Receivers SHOULD emit gate `S-3` warning when `constraints.trust_level=high` AND `ise` absent. | Receive | SHOULD | §6.5.5 |
| Receivers MUST NOT auto-route/auto-merge/auto-deploy when the corresponding `receiver_authorization.*` is `false`. | Receive | MUST | §6.5.6 |
| Receivers MUST NOT use `ise` to bypass other normative constraints (mirrors §6.3.2). | Receive | MUST | §6.5.7 |

### S3.4 — Relationship to `constraints.trust_level`

`constraints.trust_level` (coarse, three-tier) is **retained and unchanged**. `ise.*` composes with it: `trust_level` answers "how cautious should the receiver be?", `ise.*` answers "what specific authorities does the emitter claim, and what is the receiver permitted to do?". Neither field deprecates the other. Spec §6.3 prose is unchanged; §6.5 (NEW) explicitly cross-references §6.3.2 (MUST-NOT-bypass clause).

### S4.3 — Gate-check pseudocode (bash, illustrative for `S-3`)

```bash
# conformance/lib/ise.sh — gate S-3
check_s3_ise_required_at_high() {
  local env_path="$1"
  local trust ise_present
  trust="$(jq -r '.constraints.trust_level // "standard"' "$env_path")"
  ise_present="$(jq -e '.ise' "$env_path" >/dev/null 2>&1 && echo true || echo false)"
  if [ "$trust" = "high" ] && [ "$ise_present" = "false" ]; then
    warn "S-3: trust_level=high without ise.* block; see spec §6.5.5"
    return 0   # SHOULD, not MUST — return 0 to keep exit code clean.
  fi
}
```

## S5 — Migration path (v1.x → v2.0)

### S5.1 — Envelope-version acceptance regex

| Mode | Regex |
|---|---|
| v1.2 verifier (current) | `^1\.[012](\.\d+)?$` |
| **v2.0 verifier (new)** | `^(1\.[012]\|2\.0)(\.\d+)?$` |

Equivalent to scoping-doc proposal "`^[12]\.\d+(\.\d+)?$`" but **narrower** — it does not accept hypothetical v1.3 or v2.1 envelopes that don't yet exist. Future minors widen the regex per their own PRs.

### S5.2 — Required-on-v2 vs optional-during-window

## S7 — GIVEN/WHEN/THEN

### Scenario S7.1 — Emit v2 with all three ISE fields (happy path)

- **GIVEN** SPECTRA produces a spec artefact on the `spectra → apivr` edge with `trust_level=standard`.
- **WHEN** the TS SDK is called with `{ ise: { assertion_grade: "validated", provenance: { methodology_version: "spectra-4.3.1" }, receiver_authorization: { auto_route: true } } }`.
- **THEN** the emitted envelope carries `envelope_version: "2.0"`, all three ISE fields, `schema_version: "2.0"`. Gate `S-1` PASS, `E-3` PASS, `I-1` PASS.

### Scenario S7.2 — Emit v2 missing ISE (still conformant)

- **GIVEN** ATLAS produces a scout report on the `atlas → spectra` edge with `trust_level=standard`.
- **WHEN** the bash SDK `envelope-build.sh` is invoked WITHOUT `--ise`.
- **THEN** envelope is emitted at `envelope_version: "2.0"` with NO `ise` field. `E-3` PASS, `S-1` not-applicable, `S-3` not-applicable (trust_level≠high). Receiver accepts unconditionally.

### Scenario S7.3 — Emit v2 at high trust, ISE absent (S-3 warn)

- **GIVEN** APIVR-Δ emits a completion report on the `apivr → vigil` edge (`trust_level: "high"` per contract — FINDING-008).
- **WHEN** the emitter omits the `ise` block.
- **THEN** envelope passes `E-3`, `C-1`, `I-1`, `I-3`. `S-3` raises **WARN** ("trust_level=high without ise.* block; see §6.5.5"). `I-5` may *also* fire if `integrity.method=sha256` (DECISION-S8). Exit code 0; warnings on stderr.

### Scenario S7.4 — Receive v1.x envelope under v2.0 verifier (§7.3 compat)

- **GIVEN** a legacy v1.2 envelope `envelope_version: "1.2"` arrives at a v2.0-verifier-equipped SPECTRA receiver.
- **WHEN** `bash conformance/check.sh` runs.
- **THEN** `E-3` matches the expanded regex (PASS). `E-3.compat` emits INFO "v1.x envelope accepted under v2.0 receiver, §7.3 window valid through 2027-05-13". No warn, no fail. ISE gates skipped (block absent + trust_level≠high by examination).

### Scenario S7.5 — Receive v2.0 envelope under v1.2 verifier (back-compat in the OTHER direction)

- **GIVEN** a v2.0 envelope arrives at a still-deployed v1.2 verifier.
- **WHEN** the v1.2 conformance regex `^1\.[012](\.\d+)?$` evaluates `envelope_version: "2.0"`.
- **THEN** `E-3` **FAILS** at the v1.2 verifier (expected). This is **not** a v2.0 spec defect; it documents the asymmetric §7.3 contract (v2.0 SHALL accept v1.x; v1.x is NOT required to accept v2.0). The migration guide `docs/migration-v1-to-v2.md` MUST call out this asymmetry.

- **THEN** `I-5` emits SHOULD-level warning (unchanged from v1.1/v1.2). Exit code 0. `S-3` ALSO fires if `ise` absent. Two warnings stack; neither blocks.

### Scenario S7.7 — Contract schema validation per DECISION-S2 / GAP-A
