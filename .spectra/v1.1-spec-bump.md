### [DECISION-S2] — Schema `$id` versioning → **KEEP at v1.0.0 (do not churn)**

**Resolution:** All `schemas/*.json` `$id` values stay pinned at `v1.0.0`. **No schema file is modified in this PR.**

**Rationale:**

- The HMAC promotion is a **prose-level normative change** (§6.1 promotes a SHOULD to RECOMMENDED + adds a conformance gate). The JSON Schema already permits both `sha256` and `hmac-sha256` — no schema-shape change, no field added, no constraint tightened *at the schema layer*.
- Twelve schema files (six core + six per-Eidolon) would each take a `$id` bump for zero behavioural change. The cost is mechanical (`v1.0.0` → `v1.1.0` in twelve files) but produces a churn-heavy diff that obscures the actual normative change.
- `$id` semantics in JSON Schema are identity, not version. ajv resolves cross-file `$ref`s by `$id` (see `envelopeVerify.ts:128-200`). Changing `$id` would force the TS SDK to recompile schema references AND require any external vendor of the schema bundle to update their import paths.
- **Precedent:** The v1.0.1 patch release (CHANGELOG.md:9-41) added eight new contract files without touching `$id`s. The same posture applies: prose-level + conformance-level changes do not require schema `$id` bumps.
- **When TO bump:** When v2.0.0 introduces a field, removes a field, or tightens a property constraint such that a v1-conformant emitter would fail validation. That is not the case here.
- **[DRIFT-CANDIDATE-D-1]** — If a future v1.x adds a new schema field (e.g., ISE trust-hierarchy fields per Phase 2 S2.3) the `$id` should bump at *that* point. Track as a drift-register seed entry in S1.5.

### [DECISION-S3] — TS SDK version → **bump to `1.1.1`** (patch within the v1.1.x SDK family)

**Resolution:** `reference-sdk/ts/package.json` version bumps from `1.1.0` (current) → **`1.1.1`**. `ECL_VERSION_TARGET` in `reference-sdk/ts/src/version.ts` bumps from `"1.0"` → **`"1.1"`**.

**Rationale:**

- `docs/tech-choice.md:42-45` commits to lock-step minor versioning: "all three SDKs lock-step with the spec ... Patch versions per SDK MAY differ ... minor versions move together."
- The HMAC warn integration in `envelopeVerify.ts` (S1.4.c) is a **behavioural addition**, not a breaking change — verifiers that did not previously see the warn will now see it. Semantically, this is a SemVer **patch** (additive non-breaking) within the v1.1.x SDK family.
- Bumping to `1.1.1` keeps the SDK MAJOR.MINOR aligned with the spec (`1.1`) per the lock-step rule, and lets the patch number track SDK-only behavioural deltas separately from spec-text changes.
- The scaffold test in `reference-sdk/ts/src/__tests__/scaffold.test.ts:24-26` (`expect(ECL_VERSION_TARGET).toBe("1.0")`) MUST be updated to `"1.1"` as part of S1.4.c — this is a one-line edit and a one-line test edit.
- **Alternative rejected:** Bumping to `1.2.0` (minor) was considered but contradicts the lock-step rule: a TS-SDK minor bump without a spec minor bump would desynchronize the family. The opposite case (SDK stays at 1.1.0, spec at 1.1) was also rejected because shipping new code under an unchanged version number is bad release hygiene.

6. **§6** — add a new §6.4 "HMAC key lifecycle":
   > **§6.4 — HMAC key lifecycle (RECOMMENDED at trust_level=high)**
   >
   > When an emitter uses `integrity.method = hmac-sha256`, the per-thread shared secret is supplied via the `ECL_HMAC_KEY` environment variable. The key SHALL satisfy:
   >
   > - **Provisioning** — out-of-band, by the orchestrator or the operator. ECL does not specify a key-exchange protocol in v1.1; that is deferred to v2.0+ (per §8 non-goals).
   > - **Scope** — one key MAY span an entire thread (recommended), OR one key per (`from`, `to`) directed edge. The receiver MUST hold the same key value the emitter used.
   > - **Lifetime** — bound to the thread's active lifetime. Keys SHOULD NOT persist beyond `thread_id` closure.
   > - **Storage** — held only in the process environment. Implementations SHALL NOT write the key to disk, log it, or include it in trace events (see §6.2.4). The bash SDK already enforces this (`reference-sdk/bash/envelope-build.sh`); the TS SDK enforces this in `envelopeVerify.ts` and `envelopeBuild.ts`.
   > - **Rotation** — out of scope for v1.1; future minor versions MAY specify a per-message-counter rotation protocol.
   > - **Verification failure** — when `ECL_HMAC_KEY` is unset at a receiver, conformance and the TS SDK emit a warn (gate **I-3**, exit 4) per §6.2.3 — they do NOT silently pass.
7. **§6.3** — add a sentence after §6.3.2:
   > §6.3.3 — **SHOULD**: emitters at `trust_level = high` SHOULD set `integrity.method = hmac-sha256` and ensure the receiver has access to `ECL_HMAC_KEY` before emission. See §6.4 for key lifecycle.
8. **§7.4** drift register — replace the v1.0 stub:
   > **§7.4 — Drift register**
   >
   > The drift register tracks cases where the spec is stricter than what live emitters do (or vice versa). Each entry is assigned a stable identifier `D-N` and a warn-only window during which conformance checkers emit a warn-level result (exit 4) without failing the build. Entries graduate from `warn → SHOULD → MUST` across minor releases.
   >
   > The full register and its governance process live in [`docs/drift-register.md`](../docs/drift-register.md). Entries are listed there with title, evidence, warn-only window, and target-promotion version.

**Implementation sketch (bash, after the I-4 block in `integrity.sh:102-111`):**

```bash
  # I-5 (SHOULD, ECL v1.1 §6.2.6): warn when trust_level=high AND method=sha256.
  local trust_level
  trust_level="$(jq -r '.constraints.trust_level // "standard"' "$env_path")"
  if [ "$trust_level" = "high" ] && [ "$method" = "sha256" ]; then
    ecl_record "I-5" "SHOULD" "warn" "hmac_recommended_at_high_trust" \
      "trust_level=high + integrity.method=sha256 — RECOMMENDED hmac-sha256 (ECL v1.1 §6)" \
      "$env_path"
  else
    ecl_record "I-5" "SHOULD" "ok" "hmac_recommended_at_high_trust" "" "$env_path"
  fi
```
